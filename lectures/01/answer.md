## 宿題

- 取り組んだレベル：発展
- やったこと：
  - 計測用スクリプト `scripts/measure_latency.py` を作った（`uv run python -m scripts.measure_latency`）。1回の呼び出しごとに、応答時間（秒）・入力／出力／思考トークン数・成否（ok か HTTP ステータス）を `lectures/01/measurements.csv` に、回答本文を `responses.jsonl` に記録する。
  - モデル: gemini-3.5-flash-lite と gemini-3.8-flash。
  - 質問は形の違う3つ: 短い一般用語（「LoRAとは何ですか？」）、講座に固有のこと（「宿題の3レベル」）、長い入力（`problem.md` 全文を3行で要約）。
  - 各組み合わせ3回ずつ。無料枠の1分あたりの上限を超えないよう、呼び出しの間を lite は5秒、3.8-flash は14秒あけた。3.8-flash の講座固有の質問は1回も成功しなかったため、3回追加で実行した。

  失敗はすべて 503（"This model is currently experiencing high demand"）で、429（レート制限）は一度も出なかった。lite は9回中1回、3.8-flash は12回中8回が 503。503 は0.5〜11秒で返ってきた。

- 気づき・疑問：
  - **lite は出力の長さに関係なく約10〜14秒かかった。** 出力が約100トークンの要約も、約550トークンの説明も、ほぼ同じ時間だった。生成の速さより、混雑による待ち時間など一定の上乗せが応答時間を決めていたと考えられる。
  - **3.8-flash は、作ったトークン数（出力＋思考）にほぼ比例して時間がかかった。** 毎秒約78〜98トークン。そのため、出力が短い要約では lite より速く（中央値4.6秒対12.0秒）、長い説明では遅かった（17.4秒）。「上位モデルは遅い」とは一概に言えず、質問の形しだいで逆転した。
  - **3.8-flash は、回答の1.2〜3.8倍の思考トークンを使っていた。** 画面に出る回答は700トークン強でも、裏で900トークン強を使っている。見た目の回答の長さだけでは、コストや時間を見積もれない。
  - **レート制限との関係:** lite の上限は毎分15回だが、1回に約12秒かかるので、1つずつ順番に呼ぶと毎分5回ほどしか呼べない。この使い方では、上限より応答時間のほうが先に効いた。3.8-flash（毎分5回）も、長い説明を1つずつ呼ぶなら毎分3回強で、上限には届かない。一方、短い要約（約4.6秒）を待ち時間なしで続けると毎分13回になり、上限の5回をすぐ超える。上限が効いてくるのは「応答が速い」か「並列に呼ぶ」ときだと分かった。
  - **実際に困ったのはレート制限より 503 だった。** 3.8-flash は1日10〜20回ほどしか呼べないため、503 で失敗した分も、試せる回数を圧迫する。講座固有の質問だけ6回すべて失敗したが、試行回数が少なく、質問の内容が原因かどうかは判断できない。本番で使うなら、少し待ってから再試行する仕組み（指数バックオフ）と、混んでいるときは lite に切り替える仕組みが必要だと考える。
  - 疑問: 503 が返った呼び出しは、1日の上限の回数に数えられるのか。
